# Order email delivery setup

The maker view at `/maker/orders` creates editable drafts and sends through the official Resend SDK. Sending is disabled until all required settings exist. No AI service is used when sending.

## 1. Create and verify the sender

1. Create a Resend account at https://resend.com/signup.
2. Add a sending subdomain such as `mail.dianaflagstaff.com` in Resend Domains.
3. Add the DNS records Resend provides in Cloudflare DNS. Copy their actual values; do not invent SPF or DKIM values or overwrite unrelated records. Wait for Resend to mark the domain verified.
4. Create a sending-only API key restricted to that verified domain.
5. Choose a sender such as `Diana's art <orders@mail.dianaflagstaff.com>`. It must match your verified domain. Gmail cannot be used as the sending domain through Resend.

Replies always go to `dianatsoydesign@gmail.com` through Reply-To. Venmo is `@diana-flagstaff`. Cash arrangements are handled in the template.

## 2. Create the send-history database

From the website project:

```sh
npx wrangler d1 create diana-order-emails
```

Add the real database ID returned by Cloudflare to `wrangler.jsonc`:

```json
"d1_databases": [{
  "binding": "EMAIL_DB",
  "database_name": "diana-order-emails",
  "database_id": "THE_REAL_ID_FROM_CLOUDFLARE",
  "migrations_dir": "migrations/email"
}]
```

Apply the schema locally and remotely:

```sh
npx wrangler d1 migrations apply EMAIL_DB --local
npx wrangler d1 migrations apply EMAIL_DB --remote
```

Cloudflare D1 supplies atomic database writes. The email service intentionally does not fall back to Workers KV or in-memory history for sending because those cannot safely enforce concurrent-send reservations.

## 3. Add private runtime settings

Use Cloudflare Workers secrets or these commands. Enter secrets interactively; never commit real keys or passwords:

```sh
npx wrangler secret put RESEND_API_KEY
npx wrangler secret put MAKER_PASSWORD
npx wrangler secret put ORDER_EMAIL_FROM
```

Use a unique maker password of at least 16 characters, preferably generated by a password manager. The former public default is not allowed for direct sending. Existing maker cookies must be replaced by signing in again: sessions are now HMAC-signed and expire after 7 days.

For local testing use ignored `.dev.vars` with the same settings and `ORDER_EMAIL_ENABLED=false`. Do not put keys in NEXT_PUBLIC variables. Example files contain placeholders only.

Set `ORDER_EMAIL_ENABLED=true` in the Worker configuration only when verification, database migration, secrets, and a controlled test are complete. Leave it false for ordinary local development. Deploy through the project's normal deployment workflow after reviewing the change.

## 4. Check the flow before customers

1. Run `npm run test:order-email`, `npx tsc --noEmit`, and the production build.
2. In a controlled test order addressed to your own inbox, prepare a confirmation, review recipient and full message, and click Send now yourself.
3. Refresh history: distinguish provider acceptance from delivery. Verify the received email, sender, Reply-To, and line breaks.
4. Confirm a duplicate attempt does not send another copy. Test both templates before enabling normal customer use.

No real email was sent during implementation. Provider account setup, remote database creation, production configuration and deployment remain activation tasks.

## Reliability and recovery

- One business event per order and email type, with a stable provider idempotency key.
- A database reservation is written before the provider is contacted. An atomic lease prevents concurrent sends. Client controls also guard double-clicks.
- The first attempted recipient, sender, subject and body are saved. A retry must use that exact payload. Restore saved draft in the maker view after a refresh.
- Successful acceptance is recorded permanently; the UI disables sending that type again. Changing an order status never sends email automatically.
- Resend caches idempotency keys for 24 hours. Ambiguous retries are blocked after 23 hours. Check Resend manually instead of inventing a new key or bypassing the journal.
- A timeout may mean the provider accepted the email. It is never reported as definitely unsent. Retrying the same key safely retrieves the original result within the provider window.
- Definitively rejected requests are recorded and blocked for manual investigation. A deliberate resend/correction workflow is not included: use the provider dashboard after checking the original event, rather than deleting history.
- History refresh reads the saved sending result. Acceptance is not proof of delivery. Check delivery and bounce details in the Resend dashboard. This integration uses a domain-restricted sending-only key; it intentionally does not request full account access for delivery polling. Signed delivery webhooks can be added later if dashboard-free tracking is needed.
- Order status and payment records are not changed by email sending.
- Email content and recipient addresses are private customer data in D1. Only authenticated maker endpoints expose this history; no keys or passwords are sent to the browser.
- Runtime requests check same-origin, authentication, order existence and recipient matching. Recipient changes require updating the order through a separate approved workflow.

## Existing dependency audit finding

Upgrade and verify the framework in a separate change before enabling production delivery. The newly installed Resend SDK was not listed among the audited vulnerabilities. Other pre-existing dependency advisories also remain outside this email integration.
